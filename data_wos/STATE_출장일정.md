# 출장 일정 상태 - 컨설턴트의 요구사항 하나 = 상태 칸 하나

> 오늘(금)은 이 상태가 **이미 채워져 있다고 치고** 값을 판정해 업무를 처리하는 그래프를 만듭니다 (`trip_pipeline.py`). 사람 말을 이 상태로 바꾸는 일은 다음 주입니다.

## 상황 한 줄

출장 다니는 컨설턴트가 일정 에이전트에게 말합니다. 에이전트는 **방문지**를 정하고, 그곳의 **예약**을 잡고, 거기까지 **이동**을 정하고, 방문지가 갖춰야 할 **조건**을 기억합니다. 이 네 묶음이 컨설턴트의 요구사항 전부이고, 요구 하나가 상태 칸 하나입니다.

대화 1,297건 어디에서나 같은 칸을 씁니다. 대화가 진행되면 칸이 하나씩 찹니다. 다 찰 필요는 없습니다. 안 찬 칸이 되물을 자리입니다.

## 상태 칸 24개

실물 = 이 폴더의 `trip_state.py` (`TripState`). S2 에서 `BookingState` 자리에 그대로 넣습니다.

### 1. 방문지 - 이번 출장에서 가야 할 곳

| 칸 | 값 | 대화의 어느 슬롯에서 오나 | 예 |
|---|---|---|---|
| `place_kind` | 식당 / 숙소 / 관광 | 슬롯 이름 앞부분 | 관광 |
| `place_area` | 서울 중앙 / 동쪽 / 서쪽 / 남쪽 / 북쪽 / dontcare | 식당-지역, 숙소-지역, 관광-지역 | 서울 서쪽 |
| `place_type` | 식당 9종 · 숙소 2종 · 관광 11종 | 식당-종류, 숙소-종류, 관광-종류 | 한식당 / 모텔 / 랜드마크 |
| `place_price` | 저렴 / 적당 / 비싼 / dontcare | 식당-가격대, 숙소-가격대 | 저렴 |
| `place_name` | 이름 | 식당-이름, 숙소-이름, 관광-이름 | 심미 호스텔 |

출장 프레임으로 읽으면 관광 = 방문지·현장, 숙소 = 숙소, 식당 = 식사 자리입니다.

### 2. 예약 - 그곳에 언제, 몇 명, 며칠

| 칸 | 값 | 어느 슬롯 | 예 |
|---|---|---|---|
| `date` | 월요일 ... 일요일 | 식당-예약 요일, 숙소-예약 요일 | 토요일 |
| `time` | HH:MM | 식당-예약 시간 | 11:00 |
| `headcount` | 1-10 | 식당-예약 명수, 숙소-예약 명수 | 3 |
| `nights` | 1-10 | 숙소-예약 기간 | 5 |

### 3. 이동 - 방문지까지 어떻게

| 칸 | 값 | 어느 슬롯 | 예 |
|---|---|---|---|
| `move_from` | 이름 / dontcare | 택시-출발지 | 호텔 파크 |
| `move_to` | 이름 / dontcare | 택시-도착지 | 서울중앙성원 |
| `depart_time` | HH:MM / dontcare | 택시-출발 시간 | 05:10 |
| `arrive_time` | HH:MM / dontcare | 택시-도착 시간 | 11:30 |
| `vehicle` | 고급 / 에코 / 개인 / dontcare | 택시-종류 | dontcare |

**이월** = `move_to` 또는 `move_from`이 `place_name`과 같은 것. 전량 1,297건 중 934건(72%). 컨설턴트가 도착지를 다시 말하지 않아도 에이전트가 방문지 이름을 들고 가면 채워집니다.

### 4. 조건 - 방문지가 갖춰야 할 것

값은 전부 yes / no / dontcare.

| 칸 | 어느 슬롯 | 어느 방문지에 나오나 |
|---|---|---|
| `need_parking` | 식당-주차 가능, 관광-주차 가능 | 식당·관광 |
| `need_outdoor` | 식당-야외석 유무 | 식당 |
| `need_alcohol` | 식당-주류 판매 | 식당 |
| `need_smoking` | 식당-흡연 가능, 숙소-흡연 가능 | 식당·숙소 |
| `need_internet` | 숙소-인터넷 가능 | 숙소 |
| `need_gym` | 숙소-헬스장 유무 | 숙소 |
| `need_spa` | 숙소-스파 유무 | 숙소 |
| `need_breakfast` | 숙소-조식 가능 | 숙소 |
| `need_pool` | 숙소-수영장 유무 | 숙소 |
| `need_historic` | 관광-역사적 | 관광 |

## 공용 리소스 - 요구 상태와 따로 두는 것

위 24칸은 전부 **컨설턴트가 말한 것**입니다. 그런데 "이 일정이 되는가"를 판정하려면 컨설턴트가 말하지 않은 값이 필요합니다. 지금 몇 시인지, 지금 어디인지, 거기까지 몇 분 걸리는지, 앞뒤에 무슨 일정이 있는지. 이 값들은 지도·캘린더·날씨 같은 **다른 기능이 채우고 여러 기능이 같이 쓰는** 공용 값입니다. 요구 24칸과 섞지 않고 리소스 칸으로 따로 둡니다.

세 가지를 가릅니다.

| 무엇 | 뜻 | 예 |
|---|---|---|
| State (상태) | 지금 상황 | 현재 시각 06:00, 현재 위치 서울 |
| Constraint (제약) | 반드시 지켜야 하는 조건. 시간과 장소를 **비교해서** 생긴다 | 10:00 까지 도착해야 한다 / 같은 시각에 두 장소에 있을 수 없다 / 이동에는 시간이 걸린다 |
| Resource (자원) | 양이 제한된 것 | 사용할 수 있는 240분, 빈 일정 구간, 탈 수 있는 교통편 |

### 슬롯 · 리소스 · 상태 · 판정 - 오늘 넣는 네 낱말

| 낱말 | 뜻 | 오늘 실물 |
|---|---|---|
| 슬롯 | 채워야 하는 칸 하나 (이름 + 값) | 지난주 WoS 슬롯 34종 -> 요구 24칸 |
| 리소스 | 슬롯을 채우는 원천. 사용자가 말하지 않은 칸은 도구가 채운다 | 시계 · 위치 · 지도 · 달력 · 날씨 · 가용 표 · 규칙 |
| 상태 | 워크플로가 들고 다니는 전부 = 요구 슬롯 24 + 리소스 슬롯 10 + 판정 결과 4 | 표의 행 하나 |
| 판정 | 중간에서 상태를 읽고 답을 써 넣는 규칙 | 오늘 앱의 `decide` - 내가 쓴 규칙, LLM 아님 |

### Context 10칸 - 리소스가 채우는 슬롯

| 칸 | 어느 리소스가 | 뜻 |
|---|---|---|
| `event_status` | 날씨 · 주최 | 행사 자체의 상태: 예정 / 연기 / 취소. 날씨는 이동시간만이 아니라 행사도 바꾼다 |
| `place_available` | 가용 표 | 방문지가 그 날짜에 받을 수 있나: 가능 / 만석. 카페의 "품절" |

| 칸 | 어디서 오나 | 뜻 |
|---|---|---|
| `current_time` `current_location` | 시계 · 위치 | State |
| `travel_min` | 지도 도구 | 이동시간(분) - Resource 계산 재료 |
| `weather_delay_min` | 날씨 도구 | 지연(분), 없으면 0 |
| `prev_event_end` `next_event_start` `next_event_location` | 캘린더 도구 | 앞뒤 일정 |
| `prep_min` | 규칙 | 준비 여유(분). 기본 15 - **수업에서 정한다** |

### 판정 결과 4칸 - 판정이 써 넣는 슬롯

| 칸 | 뜻 |
|---|---|
| `status` | FEASIBLE / RISK / CONFLICT / INCOMPLETE |
| `reason` | 왜 그 판정인지 한 문장 (숫자 포함) |
| `required_departure` | 출발해야 하는 시각 (RISK 에 붙는 계산된 사실) |
| `alternatives` | 만석·취소일 때 제약을 만족하는 방문지 **전부, 순서 없이**. 고르는 것은 사람 - 고르면 이월이 도착지를 바꾼다 |

### 판정 4종 - 덧셈·뺄셈·비교뿐, LLM 없음

`trip_state.judge(요구, Context)` 가 냅니다. 파이프라인의 `evaluate` 노드가 이월 뒤에 부릅니다.

| 판정 | 조건 | 그 다음 |
|---|---|---|
| `FEASIBLE` 가능 | 필요 시간(이동 + 지연 + 준비) <= 사용 가능 시간(목표 시각 - 출발 가능 시각) | 계속 진행 |
| `RISK` 위험 | 필요 > 사용 가능 | 경고를 달고 계속. 출발해야 하는 시각을 같이 낸다 |
| `CONFLICT` 충돌 | 같은 시각에 다른 장소 일정 / 목표 시각이 이미 지남 | **멈춤** - 바꿀 일정을 사람이 고른다 |
| `INCOMPLETE` 정보 부족 | 목표 시각·이동시간·출발 가능 시각 중 하나가 없다 | **멈춤** - 그 값을 주는 도구를 연결하거나 사람이 준다 |

같은 요구("화요일 10시 부산 고객사")에 Context 만 다르게 넣으면 판정이 달라집니다. `python trip_pipeline.py --demo` 의 A-E 다섯 상황이 그것입니다. **여기까지는 Agent 가 아니라 상태를 반영하는 Workflow 입니다.** 판정 결과를 보고 다음 행동을 고르는 권한을 LLM 에 넘기는 순간부터 Agent 입니다 - 그건 다음 주.

WoS 실습 데이터에는 Context 가 없습니다(대화에 현재 위치·이동시간이 안 나옵니다). 그래서 `--wos` 는 요구 24칸의 완결성만 판정하고, 판정 4종은 `--demo` 에서만 나옵니다.


## 빈 칸과 dontcare 는 다릅니다

| 칸 상태 | 뜻 | 에이전트가 할 일 |
|---|---|---|
| 없음 (빈 칸) | 아직 모른다 | 되묻는다 |
| `dontcare` | 사용자가 "아무거나" 라고 말했다 | 채워진 것으로 친다. 되묻지 않는다 |
| 값 | 정해졌다 | 들고 간다 |

## 오늘 에이전트의 5칸과 이 상태의 관계

| 오늘 5칸 | 이 상태에서 | 비고 |
|---|---|---|
| `address` | `place_name` (없으면 `move_to`) | 방문지 |
| `date` | `date` | |
| `time` | `time` (없으면 `depart_time`) | |
| `customer` | **없음** | 대화에 안 나옵니다. 되물어야 정답 |
| `service` | **없음** | 같음 |

`trip_state.to_booking5()` 가 이 대응을 합니다. 채점기 기본 모드(`--fields core`)는 이 5칸만 채점하고, `--fields all` 은 24칸을 채점합니다.

## 채워지는 순서

대화는 거의 항상 **방문지 -> 예약 -> 이동** 순서입니다. 조건은 방문지를 고를 때 같이 나옵니다.

```
turn 1  방문지 종류·지역·조건        place_kind, place_area, need_*
turn 2  방문지 결정 + 예약            place_name, date, time, headcount
turn 3  이동 (도착지는 이월)          move_from, depart_time, vehicle   <- move_to 는 place_name 에서
turn 4  마무리
```

## 오늘의 질문 - 방문지 이름을 이동의 어느 끝에 넣을 것인가

파이프라인의 `carry_over` 노드는 방문지가 정해지면 그 이름을 이동의 한쪽 끝에 미리 넣습니다. 어느 끝인지가 **내가 바꾸는 규칙**이고, 데이터로 재 볼 수 있습니다.

| 데이터가 말하는 것 (마지막 상태 1,297건) | 건수 |
|---|---|
| 방문지 이름이 이동의 **도착지** | 490 |
| 방문지 이름이 이동의 **출발지** | 444 |
| 어느 쪽도 아님 (도착지 dontcare, 다른 곳 등) | 363 |

| 규칙 (`--carry`) | 사용자가 방문지를 말한 뒤 이월한 대화 | 나중에 사용자가 말한 것과 같음 | 다름 | 안 정함 |
|---|---|---|---|---|
| `to` 도착지로 (기본) | 1,255 | 484 | 677 | 94 |
| `from` 출발지로 | 1,253 | 434 | 685 | 134 |
| `none` 이월 안 함, 되묻는다 | 0 | - | - | - |

어느 규칙도 절반을 못 넘깁니다. 둘 다 열어 두고 이동 턴에서 되물을지, 방문지 종류(관광은 도착지, 숙소는 출발지가 많다)로 갈릴지는 **내 에이전트가 정하는 규칙**입니다.

```
python trip_pipeline.py --wos --all --carry to
python trip_pipeline.py --wos --all --carry from
```

숫자가 바뀌는 것을 보고 규칙을 하나 정합니다. 그 규칙이 `trip_pipeline.py` 의 `carry_over` 안에 몇 줄로 들어갑니다. 장소를 중간에 바꾼 대화(273건)에서 이미 채운 끝을 따라 바꿀지도 같은 자리에서 정합니다.
